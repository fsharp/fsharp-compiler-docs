Performance-improvement review: evidence and rule contract

This is the source-to-rule contract for the reviewer. corpus.md fixes discovery to 2026-04-22 through 2026-09-22, with evidence cutoff 2026-09-22T09:28:34Z. validation.md distinguishes frozen RED expectations, preserved failures and actual final C6 acceptance. G1-G8 are eight ordered checks, not eight unconditional benchmark demands.

Attribution correction (sprint 10): the #20348/#20352 seeds came from orchestration, not an original-user attestation of authorship. The audit below uses the captured comment, enclosing review, replies, account/role, automation disclosures and pinned source instead. source-attributed identifies what a participant posted and in which role; it does not certify unaided human composition. A User account, an empty enclosing review, absence of a model marker, interactive replies or a matching code change alone supplies no such certificate. Conversely, uncertainty is not evidence of AI authorship, and no writing-style test or external attestation prerequisite is imposed. These conversations are usable as attributed feedback with the stated limits.

All twelve rules remain request-required, independently of source attribution. Archived C5 and its extract call PERF-08/09 human-derived + request-required; that historical label is not proof of composition. Sprint 11 aligns the candidate/integration wording with source attribution, without claiming unaided composition. Its sole subsequent decision-rule repair is PERF-05's instrumentation clause, prompted by an actual missed source-backed development concern; original expectations and failures remain in validation. #20416's explicit AI disclosure applies to that review and attached inline findings. In contrast, #20261's review has no explicit automation disclosure in the captured review/comment envelopes: the earlier "model-associated" label is unsupported, so composition remains uncertain, not classified by style. Both remain excluded from verified-human votes, alongside bots, uncertain quotations, existing agents and synthetic cases. Author measurements are not independent review; code corroborates mechanisms/resolutions, not authorship.

Tooling context, not human evidence

Post-C3 evaluation correction (request-required, not new human training history): HOLD-09's frozen oracle required a modern-runtime comparison with hardware intrinsics disabled. C3 asked about .NET Framework and broader inputs but missed that condition. The final source chooses LINQ on modern runtimes and the old loop on Framework; Framework data therefore does not measure LINQ's modern scalar fallback. The earlier request is attribution-limited 2025 context, not a newly verified human precedent or in-window human vote. PERF-03 now explicitly asks for representative supported fast/fallback paths on the same runtime when capability-dependent dispatch is implicated. This is not a universal hardware/OS/runtime benchmark matrix. The original C3 output/oracle remain in validation.md; #18509 becomes development, and a coached replay cannot count as independent holdout success.

Post-C4 development-regression correction (request-required): C4 recognized HOLD-01's changed runtime array type but treated its compatibility obligation as an unspecified policy, omitting the concrete formerly successful downcast that now fails. This exposed development case was already excluded from holdout credit. PERF-06/12 distinguish representation differences requiring investigation from source-established caller failures, which are material risk even without a separate policy document. Intentional empty sharing does not automatically authorize the collateral runtime-type break. C5 makes that classification explicit; no new human precedent or changed oracle is claimed.

At checkout ae294143e5890033fcb717956050a91a6f2ed6e8, benchmark guidance distinguishes compiler/service work from generated-program runtime and cautions about environment differences. Historical FCS comparison measures FSharpChecker.ParseAndCheckFileInProject; its per-version BenchmarkDotNet processes and API compatibility defines need recording. A ParseAndCheckProject retention claim is not automatically covered by that single-file benchmark.

Compiled-program benchmarks use tests\benchmarks\CompiledCodeBenchmarks\MicroPerf\MicroPerf.fsproj. Program.fs configures Current as baseline and Preview as a custom build configuration; the project selects preview language/local compiler for that configuration. These labels are not baseline/PR commit identities. Verify the binaries, runtime, flags and compiler versions actually used on both sides.

When appropriate, BuildWithLocalFSharp.fsx supplies local compiler/core overrides after a Release packed build; its --verify mode checks the resolved FSharp.Core version in assets files, not the compiler binary's identity. Retain the actual compiler path/version separately. This is tooling choice, not a mandatory matrix or a benchmark result. The existing expert-reviewer remains responsible for broad compiler review; these rules request behavior proof only where a performance mechanism could change it.
